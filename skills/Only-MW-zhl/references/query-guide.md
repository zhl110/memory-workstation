# 读取指南

> 搜索策略、结果处理和知识图谱使用

---

## 搜索策略

### 策略 1：精准检索

**适用场景**：明确知道要找什么
- "上次 FTS5 的 tokenizer 怎么配的？"
- "之前那个 BUG 是怎么修的？"

**做法**：
```bash
mw search "FTS5 tokenizer 配置"               # 默认 top-5（搜 SQLite）
mw search "FTS5 tokenizer 配置" --include-md   # 同时搜 SQLite + 导出的 MD 文件
mw search "FTS5 tokenizer 配置" -n 3           # 控制条数
mw search "FTS5 tokenizer 配置" --explain      # 查看 FTS5/Entity/Vector 各路分数详情
```

**`--include-md` 什么时候用**：确切知道关键词时，MD 原文匹配比语义搜索更精准，也能搜到 SQLite 中因分词问题遗漏的内容。SQLite 结果在前（JSON），MD 匹配在后（文本）。

**结果处理**：直接读取最相关的 1-2 条，不需要合并。

---

### 策略 2：关联检索

**适用场景**：不确定具体内容，找相关经验
- "做过类似的功能吗？"
- "有什么相关的经验可以参考？"

**做法**：
```bash
mw search "FTS5" --extra 配置 设置 tokenizer      # --extra 扩展关键词，OR 语义扩大覆盖
mw search "FTS5" --no-vector                      # 关闭向量搜索，纯 FTS5 关键词匹配（结果更精确、更少）
```

**结果处理**：合并去重 → 按相关性排序 → 摘要精简，不能把 10 条原文全塞给 LLM。

---

### 策略 3：图谱展开

**适用场景**：结果少，需要扩展关联
- 搜索结果 < 3 条
- 需要发现间接关联的记忆

**做法**：
```bash
mw search "FTS5" --graph
```

**原理**：搜索命中的记忆通过 cross_ref 关联到其他记忆，BFS 展开 1-2 跳。

**结果处理**：
- 主结果（直接命中）：score > 0.3 的记忆
- 关联结果（图谱展开）：通过 cross_ref 连接的记忆
- 关联结果需要验证相关性，不能盲目使用

---

### 策略 4：架构优先

**适用场景**：接手项目、全局理解、大范围改动
- "这个项目整体架构是什么样的？"
- "先给我讲讲项目的整体情况"

**做法**：
```bash
# 先搜架构相关
mw search "架构 设计 模块" --extra architecture

# 再按需下钻具体模块
mw search "搜索模块 FTS5"
```

**原理**：先建立全局认知，再按需下钻，避免盲人摸象。

## 搜索行为规则

### 关键词扩展

搜索前先想变体：

| 原词 | 同义词 | 中英文互换 | 抽象/具体 |
|------|--------|-----------|----------|
| 线程竞争 | 竞态条件、mutex、并发 | thread race | 数据库锁 |
| FTS5 | 全文搜索 | full-text search | SQLite FTS |
| 部署 | 打包、发布、CI | deploy | pip install |

### 多轮搜索

```
第 1 轮：mw search "主关键词"
    ↓
结果 < 3 条？
    ↓
第 2 轮：mw search "主关键词" --extra 变体1 变体2 变体3
    ↓
结果 < 3 条？
    ↓
第 3 轮：mw search "主关键词" --graph
    ↓
合并去重 → 按 score 排序 → 使用
```

### 搜索不过滤 scope

永远搜全部记忆，scope 只用于写入时归类。不要加 `--scope` 过滤。

## 搜索结果处理

### 评分阈值

> RRF 分是**相对排序分**，不是绝对质量分。同一查询的 top-1 可能只有 0.2。不确定时用 `--explain` 查看 FTS5/Entity/Vector 各路分数的来源和权重，判断匹配靠哪路命中。

| score | 做法 |
|-------|------|
| > 0.5 | 直接引用，标注 📎 MW：#xx |
| 0.3-0.5 | 引用但注明相关性（"可能相关"） |
| < 0.3 | 换关键词再搜，不引用 |
| 0 条 | 告知"未找到相关记忆" |

### 结果合并

当搜索返回多条相关记忆时：

1. **去重**：内容相似的记忆合并，保留最完整的版本
2. **排序**：按 score 从高到低
3. **摘要**：每条用一句话概括核心
4. **标注状态**（如有）：哪些是 confirmed，哪些是 deprecated（meta JSON 用户约定，非 SDK 强制字段）
5. **标注反模式**：如果有 anti-pattern，单独列出提醒

### 时效性判断

使用旧记忆时检查：
- 这个方案现在还适用吗？
- 有没有被新方案替代？
- 当前环境和当时有什么不同？

## 知识图谱使用

### 图谱搜索

```bash
mw search-links "FTS5"              # 从知识图谱搜关联链路（找记忆之间的连接关系）
mw graph-traverse <doc_id> --hops 3  # 从指定记忆 BFS 展开
```

`search-links` 跟 `--graph` 互补：search-links 搜图本身，找到"谁和谁怎么连的"；`--graph` 从搜索结果向外展开。

### cross_ref 的价值

cross_ref 是记忆之间的关联链接。当两条记忆共享实体时，自动建立关联。

**示例**：
```
#42: FTS5 tokenizer 选择
  └─ cross_ref → #17: FTS5 空表问题（共享实体：FTS5）
  └─ cross_ref → #89: 搜索权重设计（共享实体：搜索）
```

通过 graph-traverse，可以从 #42 发现 #17 和 #89，即使搜索没有直接命中。

### 什么时候用 --graph

- 搜索结果 < 3 条，需要扩展
- 需要理解记忆之间的关联关系
- 做架构分析时，需要看到全局视图

### 什么时候不用 --graph

- 搜索结果已经足够（> 5 条）
- 需要精准匹配，不需要关联
- 时间紧迫，不需要深入探索

### 维护 cross_ref

`mw crawl` 会扫描所有记忆的实体，自动建立 cross_ref 链接。

**建议**：
- 每次大量写入新记忆后，跑一次 `mw crawl`
- 不需要频繁跑（crawl 耗时较长）
- cross_ref 质量取决于实体提取质量

## 读取后处理 Prompt

**你是记忆检索结果处理器。对检索返回的多条记忆进行整理。**

### 输入

- 检索到的多条记忆
- 查询意图

### 处理规则

1. 按相关性排序，最相关的放前面
2. 重复/相似的内容合并，保留最完整的版本
3. 每条记忆用一句话摘要 + 关键信息点
4. 标注状态（如有）：哪些是 confirmed，哪些是 deprecated（见 meta JSON 约定，非 SDK 强制字段）
5. deprecated 的记忆要说明被什么替代了
6. 如果有 anti-pattern，单独列出来提醒注意

### 输出格式

```
检索结果（共 N 条）

1. [记忆标题] ⭐ 高相关
   - 类型：规则 / 经验 / bug-fix / 架构决策 / 项目记录 / 配置
   - 状态（如有）：confirmed / deprecated
   - 摘要：一句话总结
   - 关键信息：
     · 要点1
     · 要点2

2. [记忆标题]
   ...

⚠️ 注意事项
   - [反模式] → 不要这么做，因为...
   - [废弃记忆] → 已被 [新记忆] 替代
```

## 记忆应用判断

**你是记忆应用顾问。判断检索到的记忆是否适用于当前场景。**

### 判断维度

1. **适用性**：完全适用 / 部分适用 / 不适用
2. **时效性**：这个方案现在还适用吗？
3. **上下文差异**：当前场景和记忆中的场景有什么不同？
4. **冲突处理**：如果记忆之间有冲突，说明冲突点并给出判断

### 原则

- 不要生搬硬套，记忆是参考不是标准答案
- 注意时效性，旧方案可能不适用新环境
- 注意上下文差异，A 场景的经验不一定适合 B 场景

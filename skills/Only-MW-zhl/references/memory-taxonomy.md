# 分类体系

> MW 记忆的分类维度、标签规则和决策指南

---

## 分类维度

MW 记忆有三个核心分类维度：

| 维度 | 字段 | 作用 | 可选值 |
|------|------|------|--------|
| **类型** | label | 这条记忆是什么 | 规则/经验/bug-fix/架构决策/项目记录/配置/偏好 |
| **范围** | scope | 这条记忆在哪里有效 | global/project/session |
| **重要性** | importance | 这条记忆多重要 | P0/P1/P2/P3 |

---

## 一、label（类型）

### 规则

**适用场景**：用户明确的约束、规范、禁止事项

| 特征 | 示例 |
|------|------|
| 包含"必须""禁止""不允许" | "禁止硬编码密钥" |
| 用户明确要求 | "以后都用 pnpm" |
| 项目规范 | "提交前必须跑 lint" |

**scope**：通常是 global（跨项目通用）或 project（项目专属）

---

### 经验

**适用场景**：可复用的教训、发现、最佳实践

| 特征 | 示例 |
|------|------|
| 排查结论 | "FTS5 空表时 LIKE fallback 不触发" |
| 发现更好方法 | "用 RRF 融合比加权求和更稳定" |
| 踩坑总结 | "decay 权重降太快导致好记忆被遗忘" |

**scope**：通常是 project

---

### bug-fix

**适用场景**：问题 + 根因 + 解决方案

| 特征 | 示例 |
|------|------|
| 问题描述 | "搜索返回 0 条结果" |
| 根因分析 | "FTS5 索引未同步" |
| 解决方案 | "写入后重建 FTS5 索引" |

**scope**：通常是 project

**必须包含**：问题 + 根因 + 方案 + 验证状态

---

### 配置

**适用场景**：工具、环境、参数的具体配置记录

| 特征 | 示例 |
|------|------|
| 环境要求 | “Node.js 18+” |
| 参数设定 | “HNSW ef_construction=200” |
| 工具命令 | “pyinstaller --onefile” |

**scope**：通常是 project 或 global

---

### 架构决策

**适用场景**：技术选型、方案选择、设计决策

| 特征 | 示例 |
|------|------|
| 选了什么 | "选了 RRF 融合" |
| 为什么选 | "天然归一化，不需要处理量纲" |
| 没选什么 | "没选加权求和，因为量纲不一致" |

**scope**：通常是 global（影响整个项目）或 project

**必须包含**：备选方案 + 最终选择 + 权衡理由

---

### 项目记录

**适用场景**：进展、版本、里程碑、状态

| 特征 | 示例 |
|------|------|
| 版本发布 | "MW v0.22.2 发布" |
| 里程碑 | "搜索增强完成" |
| 状态更新 | "C++ 编译通过，待测试" |

**scope**：通常是 project

**必须包含**：版本/阶段 + 做了什么 + 当前状态

---

## 二、scope（范围）

### global

**含义**：通用规则，所有项目都适用

**适用场景**：
- 安全规则（"禁止硬编码密钥"）
- 执行规范（"修改代码后必须跑测试"）
- 沟通规范（"回复使用中文"）

**加载方式**：Agent 端 always_load 列表（`mw always-load set <id>`），非 scope 自动绑定

---

### project

**含义**：项目记忆，只在该项目上下文中有效

**适用场景**：
- 项目进展（"MW v0.22.2 完成"）
- 踩坑经验（"FTS5 空表问题"）
- 架构决策（"选了 RRF 融合"）

**加载方式**：按需搜索

---

### session

**含义**：会话记忆，当前会话的上下文快照。**跨会话恢复时只读最新一条，不自动加载，自然老化。**

**用途**：
- 记录当前任务进度：改了什么、到了哪一步、阻塞什么、下一步做什么
- 记录临时上下文：正在调试的问题、待验证的假设
- 记录会话级别发现：本次会话中得到的但还没晋升为规则的知识
- 新会话启动时：只读最新一条 session 快照恢复上下文

**生命周期**：

```
 写入         活跃期           老化期             可清理
  │──────────────│──────────────│──────────────────│
  │  可正常读取   │  权重衰减     │  cold 不参与搜索  │
  │  恢复上下文  │  排位下降     │                   │
  │              │              │                   │
  ↑ 子任务完成时写  ↑ 跨会话后自然沉底   ↑ mw cleanup
```

| 阶段 | 时机 | 行为 | 说明 |
|------|------|------|------|
| 写入 | 子任务完成/compact前/会话结束 | `mw ingest --scope session` | 同 session 写"增量"，最后一条写"完整" |
| 活跃 | 写入后短期内（跨会话前） | 可被搜索/读取恢复上下文 | 新会话只读最新 1 条 |
| 老化 | 长期未访问后 | `mw decay` 统一降低 weight | 不主动读就沉底，不额外消耗 token |
| 冷化 | weight 低于阈值 | `mw evolve` 标记 cold | 不参与常规搜索 |
| 清理 | cold 且无关联 | `mw cleanup` 移除 | 确保无 cross_ref 依赖后再删 |
| 晋升 | 发现持续有用的知识 | `mw update <doc_id> --scope project` | → project scope 长期保存 |

> 具体老化速度取决于 `mw decay` 的默认参数（30 天）和该 session 记忆的实际读取频率。跨会话后不被读取，权重自然快速衰减。

**存储特点**：
- 与 project/global 记忆**同表同结构**，仅 `scope=session` 区分
- **不占 Always-Load 额度**（不在 `get_always_load(5)` 中）
- 按需加载：Agent 需要用 session 恢复时才搜索读取，不是自动注入

**与 project 记忆的区别**：
| 维度 | session | project |
|------|---------|---------|
| 目标 | 跨会话上下文恢复 | 长期知识沉淀 |
| 加载方式 | 按需搜索（最新 1 条） | 按需搜索 |
| 生命周期 | 相对较短（自然老化） | 永久 |
| 写入频率 | 每子任务（高频） | 有结论时（低频） |
| 晋升路径 | 持续出现 → `mw update --scope project` → project | 无（最高等级） |

> `scope=''`（空值）：44 条记忆的 scope 为空，等价于未指定范围，按默认逻辑处理。

## 三、importance（重要性）

### P0（不可违反）

**适用场景**：
- 安全红线（"禁止删除生产数据库"）
- 宪法规则（"修改代码前必须先理解现有逻辑"）

**说明**：导出白名单（P0/P1/P2 才导出），搜索中高权重记忆自然获得更高稳定性

---

### P1（重要）

**适用场景**：
- 常用规则（"提交前跑 lint"）
- 关键经验（"FTS5 索引必须重建"）
- 架构决策（"搜索用 RRF 融合"）

**说明**：导出白名单内，进化时参与热候选判断

---

### P2（一般）

**适用场景**：
- 临时记录（"今天调试了 3 小时"）
- 参考资料（"这个 API 的用法"）
- 配置细节（"端口号是 8080"）

**说明**：导出白名单内，热候选优先级低于 P0/P1

---

### P3（低价值）

**适用场景**：
- 一次性调试记录
- 自动分类打入的低价值噪音

**说明**：不在导出白名单中（`mw export` 过滤掉），不影响搜索排序。CLI 不支持手动设为 P3，由系统自动分类生成。

> P4 为 JSON 日志专用，系统内部使用，Agent 无需关注。

---

## 四、分类决策树

```
内容进来
    │
    ▼
是规则/约束？
├─ 跨项目通用？ → label=规则, scope=global, importance=P0
└─ 项目专属？ → label=规则, scope=project, importance=P1
    │
    ▼
是项目相关？
├─ 进展/版本？ → label=项目记录, scope=project, importance=P1
└─ 架构决策？ → label=架构决策, scope=global, importance=P1
    │
    ▼
是踩坑/bug？
└─ label=bug-fix, scope=project, importance=P1
    │
    ▼
是经验/发现？
└─ label=经验, scope=project, importance=P1
    │
    ▼
是配置/参数/工具命令？
└─ label=配置, scope=project or global, importance=P1
    │
    ▼
是用户偏好？
└─ label=偏好, scope=global, importance=P0
```

## 六、tier（层级）

tier 不是分类，而是记忆的生命周期状态：

| tier | 含义 | 自动条件 | 手动设置 |
|------|------|---------|---------|
| hot | 活跃记忆 | 频繁访问 | `mw tier set <id> hot` |
| warm | 普通记忆 | 默认状态 | `mw tier set <id> warm` |
| cold | 归档记忆 | 长期未访问 | `mw tier set <id> cold` |
| frozen | 冻结记忆（0 条） | — | `mw tier set <id> frozen` |

**与 importance 的区别**：
- importance = 这条记忆多重要（固定属性）
- tier = 这条记忆当前多活跃（动态状态）

---

## 七、status（用户约定，非 SDK 分类字段）

> status 不是 SQL 字段，而是嵌入 meta JSON 的可选约定。SDK 不强制也不自动管理。以下分类供 Agent 自行参考。


```json
{"always_load": 0, "status": "confirmed"}
```

| status | 含义 | 使用场景 |
|--------|------|---------|
| confirmed | 已确认落地 | 大多数记忆 |
| draft | 探讨中 | 不确定要不要记时先标 draft |
| deprecated | 已废弃 | 被新方案替代的旧记忆 |
| anti-pattern | 反模式 | 错误做法的记录 |

**状态流转**：
```
draft → confirmed（反思时确认）
confirmed → deprecated（被新方案替代）
任何状态 → anti-pattern（发现是错误做法）
```

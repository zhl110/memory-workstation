# 写入指南

> 完整的写入流程、Prompt 模板和质量标准

---

## 写入流程

```
用户说"记住 XXX"
    │
    ▼
Step 1: 前置过滤
    ├── 去掉无意义对话、试探性想法
    ├── 只保留确定结论
    └── 不值得记的内容 → 跳过（见 SKILL.md "什么不值得记"）
    │
    ▼
Step 2: 搜索已有记忆（搜索优先协议）
    ├── mw search "关键词" — 判断语义上是否已有相关内容
    ├── 找到相关记忆（score > 0.3）？
    │   ├─ 是 → Step 3a：更新已有（合并或补充）
    │   └─ 否 → Step 3b：新建
    │
    ▼
Step 3a: 更新已有记忆
    ├── 改元数据：mw update <doc_id> --scope/--category/--keywords
    ├── 改层级：mw tier set <doc_id> hot（频繁访问）
    └── 追加内容：当前无直接 CLI append，重新 ingest 覆盖
    │
    ▼
Step 3b: 新建记忆
    ├── 分类：按决策树选 label/scope/importance
    ├── 结构化：按模板组织内容
    ├── 质量检查：10 分量表 >= 6 分
    └── 写入：mw ingest "内容" --label "..." --scope "..." --summary "..."
    │       └── SDK 自动去重（安全网，无感）：
    │           ├── MD5 精确匹配 → 完全相同的文本自动跳过
    │           ├── 向量余弦 > 0.99 → 近乎相同的长文本自动跳过
    │           └── Agent 无需感知，照常写入即可
    │
    ▼
Step 4: 建立关联（可选）
    ├── 写入时顺便建图谱（推荐）：加 --crawl
    │   mw ingest "内容" --crawl
    │   → 写入后自动增量扫描关联，不用单独跑 mw crawl
    ├── 搜索到相关记忆 → 显式关联
    │   mw link <新doc_id> <相关doc_id> --weight 2.0 --note "Agent 显式关联"
    └── 后续可 mw crawl 补充遗漏关联
```

> **搜索优先 vs SDK 去重**：搜索优先是 Agent 做的**语义合并判断**（这个主题是否已有记忆），SDK 去重是引擎做的**文本级防重复**（完全一样的内容别存两遍）。两者是互补的两层，不冲突。搜索优先决定"要不要合并"，SDK 去重确保"不会存一模一样的两条"。

## 前置过滤 Prompt

**你是记忆筛选器。从原始对话/代码中提取值得长期保存的内容。**

### 值得保存

- 可复用的经验、技巧、最佳实践
- 踩坑记录和解决方案
- 技术决策和选型理由
- 代码改动的核心逻辑和原因
- 项目规则、约束、规范
- 未完成的待办事项

### 不需要保存

- 纯闲聊、问候、客套话
- 临时测试、一次性的调试内容
- 已经被推翻且无参考价值的错误思路
- 重复的、和已有记忆完全一样的内容
- 过于细节、脱离上下文就看不懂的操作步骤

### 输出判断

问自己三个问题：
1. **下次遇到类似问题，这条记忆能帮到我吗？** → 不能 → 不记
2. **这条记忆有独立的上下文吗？** → 没有（需要其他记忆才能理解）→ 考虑合并
3. **这条记忆已经被其他记忆覆盖了吗？** → 是 → 不记

## 写入模板

### 规则类（scope=global）

```bash
mw ingest "
## 规则：{规则名称}
- **内容**：禁止/必须做什么
- **原因**：为什么有这个规则
- **适用场景**：什么场景下这个规则生效
- **例外**：什么情况下可不遵守
- **相关文件/工具**：（可选）配置文件路径、lint 规则名等
" --label "规则" --scope global --category "安全类" --summary "一句话摘要"
```

### 项目记录类（scope=project）

> 项目里程碑用此模板。**日常进度的频繁快照请用 `scope=session` 的会话快照模板。**

```bash
mw ingest "
## 项目：{项目名称} — {本次改动简述}
- **阶段/版本**：vx.x.x
- **时间**：yyyy-mm-dd
- **改了什么**：
  - 文件：src/xxx/yyy.ts — 改了 Z 函数，加了 xx 参数
  - 文件：src/xxx/zzz.ts — 新增了 WW 组件，处理 OO 情况
  - 新增依赖：lodash@4.17.21（用于深层拷贝）
- **改动原因**：
- **当前状态**：待办 / 进行中 / 已完成 / 阻塞
- **阻塞/风险**：（可选）依赖其他 PR、待测试等
- **下一步**：（可选）
" --label "项目记录" --scope project --category "项目记录" --summary "一句话摘要"
```

### 会话快照类（scope=session）

> **跨会话上下文恢复的核心机制。** 每次任务到一个节点（或即将 context compact 前），Agent 自动写一条。新会话启动时读取最近的 session 快照来恢复现场。
>
> **第一原则：恢复精准。** 下个窗口拿到这条记忆，不需要翻其他资料就能直接继续干活。写够再考虑精简重复。

```bash
mw ingest "
## 会话快照：{项目/任务名}
- **时间**：yyyy-mm-dd HH:mm
- **任务目标**：本轮在做什么、为什么做
- **已完成的改动**：
  - 文件：src/xxx/yyy.ts — 改了 Z 函数（加 isRefreshing 锁避免并发）
  - 文件：src/xxx/zzz.ts — 新增了 WW 组件
  - 新增依赖：xxx@1.0.0（用途说明）
- **验证结果**：改了之后效果如何、是否跑过测试
- **阻塞/风险**：（必填，没有就写"无"）卡在什么地方、等什么外部条件
- **当前进度**：第 X 步 / 总共 N 步
- **下一步**：（必填，具体可执行的操作）
- **本轮关键发现**：（可选）不记就会丢的结论/经验
" --label "项目记录" --scope session --category "会话快照" --summary "一句话摘要"
```

> **新会话启动时**：
> 1. `mw list -c "会话快照"` 列出所有快照，取最新的 doc_id
> 2. 读完整 `content`（不是只读 compact），因为恢复上下文需要细节
> 3. 如果有多条 session 记录，只读最新那条（前面的已经过时）
> 4. 确定下一步从哪开始继续
>
> **晋升**：如果 session 快照里的知识反复用到，`mw update <doc_id> --scope project` 升为 project scope 长期保存。

**避免重复的实践经验**：同一 session 内写多条快照时，后面的不必重复前面的已改动列表，只写"增量"部分。但最新那条（用于下次会话恢复的）必须包含完整上下文。

### 踩坑经验类（scope=project）

```bash
mw ingest "
## 踩坑：{问题名称}
- **项目**：xxx
- **相关文件**：（可选）涉及的源码路径
- **问题描述**：
- **触发条件**：
- **根因**：
- **解决方案**：
- **验证结果**：✅ 已修复 / ⏳ 待验证
- **教训/可复用**：下次如何避免/快速定位
" --label "bug-fix" --scope project --category "踩坑经验" --summary "一句话摘要"
```

### 架构决策类（scope=global/project）

```bash
mw ingest "
## 决策：选了 X 没选 Y
- **背景**：
- **方案对比**：X（特点/代价） vs Y（特点/代价）
- **选择理由**：
- **影响范围**：
- **涉及模块**：（可选）哪些文件/模块受此决策影响
" --label "架构决策" --scope global --category "系统架构" --summary "一句话摘要"
```

### 经验发现类（scope=project）

```bash
mw ingest "
## 经验：{发现名称}
- **场景**：什么情况下发现的
- **发现**：具体发现了什么
- **原因**：为什么会这样
- **适用条件**：哪些条件下这个经验成立
- **反例**：（可选）什么情况下不适用
- **可复用性**：其他项目/场景能否套用
" --label "经验" --scope project --category "踩坑经验" --summary "一句话摘要"
```

### 配置/参数类（scope=project or global）

```bash
mw ingest "
## 配置：{配置名}
- **工具/环境**：什么工具或环境的配置
- **参数/命令**：具体的配置值或命令
- **作用**：这项配置解决了什么问题
- **注意事项**：（可选）副作用、依赖条件
" --label "配置" --scope project --category "配置管理" --summary "一句话摘要"
```

### 用户偏好类（scope=global）

偏好没有固定模板，因为用户的偏好可以是任何方面：工具链、代码风格、命名习惯、沟通方式、工作流程、架构风格……关键是**把用户表达过且以后会用到的倾向记下来**。参考结构（不必全填）：

```bash
mw ingest "
## 偏好：{偏好的核心内容}
- **具体描述**：用户怎么说/怎么做的
- **证据**：（可选）用户原话或重复出现的模式
- **适用范围**：（可选）哪些项目/场景下有效
" --label "偏好" --scope global --category "用户偏好" --summary "一句话摘要"
```

## 真实示例

### 示例 1：记录规则

```bash
mw ingest "## 规则：打包前必须验证语法
- **内容**：运行 python -c 'import src.main' 验证
- **原因**：避免语法错误导致打包失败
- **适用场景**：所有 Python 项目打包前 CI 步骤
- **例外**：无
- **相关文件/工具**：setup.py / pyproject.toml 构建脚本" --label "规则" --scope global --category "代码类" --summary "打包前必须运行 python -c 验证语法"
```

### 示例 2：记录踩坑

```bash
mw ingest "## 踩坑：LIKE fallback 不触发
- **项目**：MW 搜索
- **相关文件**：mw_sdk/client.py _search_pool() 方法
- **问题**：FTS5 空表时 LIKE 回退未生效，搜索返回 0 条
- **触发条件**：刚初始化数据库尚未写入任何分词数据时
- **根因**：fts_pending_rebuild 队列未处理，FTS5 索引表为空
- **解决方案**：写入后调用 mw rebuild-fts5 重建索引
- **验证结果**：✅ 已修复
- **教训/可复用**：FTS5 相关操作后检查 fts5_behind 状态" --label "bug-fix" --scope project --category "踩坑经验" --summary "LIKE fallback 修复，FTS5 重建"
```

### 示例 3：记录决策

```bash
mw ingest "## 决策：搜索融合选了 RRF 没选加权求和
- **背景**：搜索需要融合 FTS5 + Entity + Vector 三路结果
- **方案对比**：加权求和（简单但三路 score 量纲不一致，调权要靠拍脑袋）vs RRF（每路各自排 rank 后按 1/(k+rank) 融合）
- **选择理由**：RRF 天然归一化，不需要处理不同量纲，k=60 业界标准值
- **影响范围**：mw_sdk/client.py search() 方法，所有搜索结果排序
- **涉及模块**：mw_sdk 搜索层、排序层" --label "架构决策" --scope global --category "系统架构" --summary "搜索融合选 RRF 因为天然归一化"
```

## 记忆粒度准则

> Agent 默认倾向写短，结果导致下次读时连不上。以下规则强制提升粒度。

### 一条好记忆必须满足

- **脱离对话可独立理解** — 假设 3 个月后回看，不需要重读上下文也能看懂
- **有具体锚点** — 文件名、函数名、版本号、技术名词（这是 entity 提取和 cross_ref 的关键）
- **有时间/版本上下文** — 知道这是什么时候、什么版本下的结论
- **有价值信号** — 明确是"已验证"还是"待验证"，"已采纳"还是"已废弃"

### 粒度对照表

| ❌ 太短（不可接受） | ✅ 足够详细 |
|-------------------|------------|
| 修复了 token 过期问题 | 修复 src/auth/interceptor.ts token 过期无刷新 — 加 isRefreshing 锁+请求队列重放 |
| 用户反馈模块重构完成 | 用户反馈模块：列表页 useState→useReducer，详情页拆成 FeedbackDetail/FeedbackHistory 俩组件，API 层加了缓存 |
| 记录一个经验，Docker 构建要注意 | Docker 构建时 pip install 后要 `--no-cache-dir`，否则基础镜像层缓存会导致旧依赖不更新 |
| 完成了分页功能 | 完成了 `usePagination` hook：支持 page/pageSize/total，配合 `react-query` 做预加载下一页 |

### 场景分段原则

一个任务过程不是一条记忆，按视角拆成多条：

| 视角 | label | 典型内容 |
|------|-------|---------|
| 任务进度 | 项目记录 | 改了什么文件、当前状态、阻塞项、下一步 |
| 可复用知识 | 经验 | 新学到的技巧、发现的规律、适用条件 |
| 修了什么坑 | bug-fix | 问题表象→根因→修复方案→验证 |
| 做了哪些决策 | 架构决策 | 选项对比、选择理由、影响范围 |
| 用户喜好/习惯 | 偏好 | 用户的强硬偏好、工作习惯、代码风格要求 |

每次写入前自问：**这条内容属于哪几个视角？有没有串在一起的东西要拆开记？**

### 写前自检（10 分量表速查）

按 SKILL.md 四维度自检：

| 维度 | 满分 | 自问 | 扣分点 |
|------|------|------|--------|
| 独立性 | 3 | 脱离对话可独立理解？ | 依赖上下文才能看懂 −2 |
| 锚点密度 | 3 | 文件名/函数名/技术名 >= 3？ | 无具体名词 −2；只有 1 个 −1 |
| 可检索性 | 2 | title+keywords 变体够广？ | 无变体 −1；title 是截取开头 −1 |
| 价值信号 | 2 | 有已验证/待验证/已废弃？ | 无状态 −1 |

**总分 ≥ 6 才写，< 6 补充后再写。**

### 搜索友好（Searchability-First）

**写 summary 和 keywords 时，先想"别人以后会搜什么词来找这条"，不是你做了什么，是别人会问什么问题。**

| ❌ 技术视角 | ✅ 搜索视角 |
|------------|-----------|
| `extra_keywords 空值 SQL OR 修复` | `mw search --extra 传空值报错` |
| `搜索权重调优完成` | `搜索不准的修复：调整 RRF 权重` |

**Keywords 必须中英文成对**：
```bash
# ✅ 好的：中英文都有
--keywords "搜索不准 RRF 权重 FTS5 recall search quality"

# ❌ 只写一种语言
--keywords "搜索权重"
```

## 质量检查清单

写入前检查：

- [ ] title 有意义（不是"规则""记录"这种空泛标题）
- [ ] 内容有完整上下文（背景+过程+结果，不只是结论）
- [ ] 内容包含具体文件名/函数名/技术名词（至少 2 个实体锚点）
- [ ] keywords 至少 3 个且中英文成对（如 "搜索权重 search weight"）
- [ ] summary 是用用户搜索视角写的（不是技术实现视角）
- [ ] 自检：三个月后搜什么词能找回这条？
- [ ] 有时间信息
- [ ] compact_content 至少 20 字（SDK 自动生成，Agent 不用手动填）
- [ ] summary 不超过 60 字
- [ ] 脱离当前对话后仍能独立理解

## status 状态管理（用户约定，非 SDK 内置）

> SDK 不强制 status 字段，以下是在 meta JSON 中可选使用的约定。

```json
{"always_load": 0, "status": "confirmed"}
```

| status | 含义 | 使用场景 |
|--------|------|---------|
| confirmed | 已确认落地 | 大多数记忆 |
| draft | 探讨中，未最终确定 | 不确定要不要记时先标 draft |
| deprecated | 已废弃，保留备查 | 被新方案替代的旧记忆 |
| anti-pattern | 反模式，专门避坑 | 错误做法的记录 |

**设置方法**：通过 Python SDK 直接操作 meta JSON 字段。

## 写入后验证

写入完成不代表能搜到。每条记忆写入后必须验证可检索性：

```bash
mw search "刚写入的核心关键词" -n 1    # 确认能搜到
```

| 验证结果 | 含义 | 处理 |
|---------|------|------|
| 能搜到，score > 0.3 | ✅ 写入成功 | 完成 |
| 能搜到，score < 0.3 | ⚠️ 排名偏低 | `mw tier set <doc_id> hot` 提升权重 |
| 搜不到 | ❌ FTS5 索引滞后 | `mw rebuild-fts5` 重建索引后重试 |

> 搜不到最常见原因：FTS5 索引写入时有延迟。等几秒或 `mw rebuild-fts5` 就好了。

# MW 记忆系统

> **SDK 是存储引擎，你是记忆的大脑。** 记不记、记什么、怎么分类、什么时候读、读了之后怎么用，全部由你按本规范判断执行。SDK 只做一件事：按你的指令存和取。

## 每会话启动

**这是你醒来后做的第一件事。** 以下文件不存在则从 `assets/` 复制模板。

| 文件 | 内容 | 为什么必读 |
|------|------|-----------|
| `MW-SOUL.md` | 你的身份、原则、违规记录 | 知道"我是谁" |
| `MW-USER.md` | 用户画像、偏好、当前项目 | 知道"我在服务谁" |
| `MW-TOOLS.md` | CLI 参数陷阱、常见错误 | 知道"工具怎么用" |

**核心原则：非阻塞。** 文件缺失不阻碍工作，Agent 按最低可行配置运行，在对话中自动积累补全。

### 启动流程

```
Step 1: 检查文件是否存在
    │
    ├─ 全在且有内容 → 依次读取 → [恢复流程]
    │
    └─ 缺失或空模板 → 自动补默认值，不阻塞，直接走 [恢复流程]
        ├── MW-SOUL.md → 默认身份："MW 记忆系统代理"
        ├── MW-USER.md → 默认称呼："用户"（问一次名字后更新）
        └── MW-TOOLS.md → 依赖 SKILL.md CLI 速查表
```

### 状态跃迁路径

三个文件不是"填好就完了"，是**一直在积累**的：

```
不存在 ──自动复制──► 空模板 ──观察自动写入──► 部分填好 ──继续积累──► 越用越全
                         ▲                            ▲
                   问一次称呼（唯一例外）          其余全部自动
                   问完直接写入                     不等用户说"记"
```

### 每个文件如何从空到满

| 文件 | 默认值（空时用） | 谁填 | 什么时候填 |
|------|----------------|------|-----------|
| MW-SOUL.md | 来自 SKILL.md 核心原则 | Agent 自动 | 用户纠正行为时 → 直接追加违规记录 |
| MW-USER.md | 称呼="用户" | 问一次 + Agent 自动 | ① 首次会话问一次"怎么称呼"→ 写入；② 检测到偏好/项目状态 → 直接写入 |
| MW-TOOLS.md | 依赖 SKILL.md CLI 速查 | Agent 自动 | 踩到 CLI 坑发现参数陷阱 → 直接写入 |

**关键区别：Agent 不问"要不要记"，直接写。**

唯一的一次询问：MW-USER.md 没有称呼时，**首个会话问一次**"怎么称呼你？"。问完直接写入，之后不再问。

### 自动积累场景

以下信号由 [WAL 协议](#前置写入协议wal) 或日常执行触发，Agent **不询问直接写入对应文件**：

| 信号 | 写入到 | 写入内容 |
|------|--------|---------|
| 用户纠正了你的行为 | MW-SOUL.md 违规记录 | 纠正内容 + 正确做法 |
| 用户说"我喜欢/我更喜欢/用 X" | MW-USER.md 偏好 | 偏好描述 + 上下文 |
| 用户说了当前项目/进度 | MW-USER.md 当前项目状态 | 项目名 + 阶段 |
| 你踩了 mw CLI 的坑 | MW-TOOLS.md | 参数 + 陷阱 + 正确用法 |

> 不询问的原因：WAL 协议已经保证了"值得记"。如果每条都问"要记吗"，用户会被烦死。相信 WAL 的判断，直接记。

### 渐进式画像构建（Drip 模式）

MW-USER.md 不能指望一次填完。用户没义务花时间填你的模板。用 **Drip 模式**——每会话自然地问 1 个问题，融入对话，不打扰。

**总画像清单（按优先级排序）：**

| 优先级 | 信息 | 自然问法 | 获取方式 |
|--------|------|---------|---------|
| P0 | 称呼 | "我怎么称呼你？" | 首个会话直问一次 |
| P1 | 工作领域 / 角色 | "你主要做什么方向？" | 自然对话或第 2-3 会话问 |
| P1 | 沟通偏好（简洁/详细/中文/英文） | — | 从对话中自动推断+确认 |
| P2 | 主要项目 / 当前目标 | "最近在忙什么项目？" | 自然对话中提取 |
| P2 | 工具链偏好（IDE/包管理器等） | — | WAL 自动积累，不需问 |

**执行规则：**

1. **每会话最多 1 个问题** —— 问完一个就停，不搞"顺便再问一个"
2. **自然地融入** —— 不是"问题2：你的角色是什么？"，而是"我先了解一下你的背景，这样后面的建议会更准——你主要做什么方向？"
3. **用户忙/跳过** —— 不追问，切到 Skip 模式，从自然对话积累
4. **用户厌烦** —— 立刻停，切到 Skip 模式，永远不再主动问
5. **机会主义填充** —— 用户在任何时候说了相关信息，直接写入对应字段，把该问题标记为已答

**检测到厌烦信号：**
- 用户回复很短/不耐烦
- 用户说"先干活"、"直接做"、"先别问"
- → 立刻停，切换到完全依赖自然对话积累

> Drip 模式和之前的"问一次称呼"不冲突。称呼是 P0，首个会话必问。其他信息按优先级，在后续会话中遇机会再问。从来没机会就永远不问，Agent 照样能干活。

## 前置写入协议（WAL）

**核心规则：先写再回复。** 每条用户消息都要扫描以下信号，**不管用户有没有说"记住"**。检测到信号 → 立即 `mw ingest` → 再组织回复。

### 触发信号

| 信号 | 识别关键词 | 写入动作 |
|------|-----------|---------|
| ✏️ 纠正 | "不对""应该是""不是""别再""不要" | `mw ingest "正确内容" --label 规则 --scope ...` |
| 🎨 偏好 | "我喜欢""我更喜欢""用X""记住我总是" | `mw ingest "偏好内容" --label 偏好 --scope global` |
| 📋 决策 | "就X吧""用X方案""决定用选X" | `mw ingest "决策内容" --label 架构决策 --scope ...` |
| 🐛 踩坑/bug | "找到原因了""原来是因为" | `mw ingest "根因+方案" --label bug-fix --scope project` |
| 🔢 具体值 | 端口号、路径、版本、配置值 | 合并入关联的决策/偏好中 |
| 📦 会话存档 | 子任务完成 / context compact / "先到这" | `mw ingest "会话快照: {项目} 进度={} 下一步={}" --scope session --label 会话快照 --keywords 会话快照 <项目>` |
| 📍 专有名词 | 人/产品/项目名第一次出现 | 不单独写，合并到上下文恢复时使用 |

### 执行规则

1. **先写再回复** — 检测到任一信号，先 `mw ingest` 再回复
2. **合并写入** — 同一消息出现多个信号，合为一条
3. **频率上限** — 每轮对话最多写 1-2 条，避免噪音
4. **用户说"不用记"** — 跳过本轮所有信号
5. **写入后仍走** [搜索优先协议](#搜索优先协议) 判断合并还是新建

## 写入规范

### 什么值得记

- 用户明确的规则/约束（"必须用 pnpm"）
- 用户的纠正（"不对，应该是..."）
- 用户的偏好（"我更喜欢..."）
- 排查结论（根因 + 解决方案）
- 架构决策（选了什么 + 为什么）
- 踩坑记录（问题 + 条件 + 方案）
- 项目进展（版本 + 里程碑 + 状态）
- 可复用的核心代码 / 关键实现细节 / 参数调试结论
- 复杂场景的完整实现方案与使用方式

### 什么不值得记

- 临时任务状态（用 task 工具）
- 一次性的问答
- 已经在 CLAUDE.md 里的内容
- 未经验证的推断
- 整段对话记录（用 chat-archive）

### 分类决策树

```
用户说"记住 XXX"时：
├─ 是规则/约束？
│   └─ 跨项目？ → label=规则, scope=global, importance=P0
│   └─ 项目专属？ → label=规则, scope=project, importance=P1
├─ 是项目相关？
│   └─ 进展/版本？ → label=项目记录, scope=project, importance=P1
│   └─ 架构决策？ → label=架构决策, scope=global, importance=P1
├─ 是踩坑/bug？
│   └─ label=bug-fix, scope=project, importance=P1
├─ 是经验/发现？
│   └─ label=经验, scope=project, importance=P1
└─ 是用户偏好？
    └─ label=偏好, scope=global, importance=P0
```

### 搜索优先协议

**写入前必须先搜索：**

```
mw search "相关关键词"
    ↓
找到相关记忆（score > 0.3）？
├─ 是 → 更新已有：mw update <doc_id> --scope/--category/--keywords
│       或：mw tier set <doc_id> hot（提升层级）
└─ 否 → 新建：mw ingest "内容" --label "..." --scope "..." --summary "..."
```

### 结构化要求

每条记忆必须包含：
1. **title**：一句话概括核心（不是截取开头）
2. **compact_content**：背景 + 过程 + 结果 + 经验（至少 20 字）
3. **keywords**：3+ 个关键词（中英文，便于搜索）
4. **时间**：什么时候的
5. **summary**：一句话概括（不超过 60 字）

### 质量标准 —— 10 分量表

每条记忆写入后，Agent 按以下 4 个维度自评打分。**总分 < 6 → 补充内容后再写。**

| 维度 | 满分 | 问题 |
|------|------|------|
| 独立性 | 3 | 脱离当前对话，三个月后回看能独立理解吗？ |
| 锚点密度 | 3 | 包含 >= 3 个具体名词（文件名/函数名/技术名/版本号）？ |
| 可检索性 | 2 | title + keywords 质量高、变体覆盖好？ |
| 价值信号 | 2 | 有明确状态（已验证/待验证/已采纳/已废弃）？ |

**优秀（9-10）：** 独立成文，锚点丰富，换 3 种关键词都能搜到，状态明确
**合格（6-8）：** 上下文完整，有足够锚点，能搜到，有状态
**不合格（< 6）：** 缺少上下文或锚点，搜不到可能，需补充后重写

对照反面——写前先验一遍：
- ❌ 只有一句话（"测试通过"）→ 独立性 0，必 < 6
- ❌ 没有上下文（"修复了一个 bug"）→ 锚点密度 0
- ❌ 没有关键词（搜不到）→ 可检索性 0
- ❌ 标题是截取开头 → 可检索性降级

### 搜索友好（Searchability-First）

**核心原则：写 summary/keywords 时，先想"用户以后会搜什么来找这条"。** 不是写你做了什么，是写别人怎么找到你。

| 反面（技术视角，❌） | 正面（搜索视角，✅） |
|---------------------|--------------------|
| `修复了 extra_keywords 空值 SQL OR 多了一个` | `mw search --extra 传空值报错，SQL OR 多了个空条件` |
| `完成搜索权重调优` | `搜索不准的修复：调整了 RRF 权重让 FTS5 不被向量淹没` |
| `LLM classify 规则匹配逻辑优化` | `写入分类不准：keyword 命中规则走 LLM 兜底` |

**Keywords 必须中英文成对：**

```bash
# 好的 keywords
--keywords "搜索权重 search weights RRF FTS5 融合"

# 不好的 keywords
--keywords "搜索权重"           # 没有英文，英文搜索命中不了
--keywords "search optimization" # 没有中文，中文搜索命中不了
```

**自检三问**（每条记忆写完后先问自己再提交）：
1. 如果我自己三个月后忘了这事，我会搜什么词来找？
2. 这些词在 summary 里出现了吗？在 keywords 里出现了吗？
3. 中英文都覆盖了吗？

### 写入后验证

写入完成不代表能搜到。每条记忆写入后必须验证可检索性：

```bash
mw search "刚写入的核心关键词" -n 1    # 确认能搜到
```

| 验证结果 | 含义 | 处理 |
|---------|------|------|
| 能搜到，score > 0.3 | ✅ 写入成功 | 完成 |
| 能搜到，score < 0.3 | ⚠️ 排名偏低 | `mw tier set <doc_id> hot` 提升权重 |
| 搜不到 | ❌ FTS5 索引滞后 | `mw rebuild-fts5` 重建索引后重试 |

> 搜不到最常见原因：FTS5 索引写入时有延迟。等几秒或 `mw rebuild-fts5` 就正常。

### 写入后反馈

> Agent 默默记了，但用户不知道你记了什么。这会让用户失去掌控感。在合适的时候给一次轻量确认。

**触发条件**（满足任意一条）：
- 本会话累计记录了 2 条以上的新记忆
- 本会话更新了 MW-USER.md（用户画像发生变化）
- 用户明确问"你记了什么"

**格式**：在回复末尾（或对话有自然断点时）附带一句：

```
对了，今天记录了几条新信息：
- 偏好：用 pnpm 管理依赖（下次直接执行）
- 经验：FTS5 空表时重建索引（已记入 MW）

如果有不对的告诉我。
```

**规则：**
1. **不每条都反馈** —— 只在有"值得说"的内容时才提，每会话最多 1 次
2. **用户说"不用告诉我"** —— 永久关掉反馈，不再提
3. **用户纠正** —— 纠正内容按 WAL 协议自动更新对应记忆
4. **反馈内容**只包含**本会话新增或变更的信息**，不重复此前已反馈过的

## 读取规范

### 搜索策略

| 策略 | 场景 | 做法 |
|------|------|------|
| MD 精准搜索 | 确切知道关键词 | `rg "关键词" memory_export_all/` 或 `mw search "关键词" --include-md` — 原文匹配，最准 |
| SQLite 语义搜索 | 记不清关键词、想找相关的 | `mw search "模糊描述"` — FTS5 + vector 两路（需关联时加 `--graph`） |
| 关联检索 | 找相关经验 | `mw search "FTS5" --extra 配置 设置` |
| 图谱展开 | 结果少时扩展 | `mw search "FTS5" --graph` |
| 架构优先 | 先了解全局 | 先搜 architecture 相关，再按需下钻 |

**MD vs SQLite 选择逻辑：**
```
确切关键词（如"WAL协议"）→ grep MD 文件 或 mw search --include-md（最准，0 token）
模糊/相关（如"上次那个用户说的问题"）→ mw search SQLite（语义匹配广）
需要关联（如"这个决策影响了什么"）→ mw search --graph
拿不准 → 先 --include-md，不够再 mw search --graph
```

### 搜索行为规则

1. 想变体：同义词、中英文互换、抽象/具体
2. `mw search "主关键词" --extra 变体1 变体2`
3. 结果 < 3 条 → 换变体再搜
4. 两轮都 < 3 条 → 加 `--graph` 展开图谱
5. 合并去重后按 score 排序使用

### 搜索结果使用

| score | 做法 |
|-------|------|
| > 0.5 | 直接引用，标注 📎 MW：#xx |
| 0.3-0.5 | 引用但注明相关性 |
| < 0.3 | 换关键词再搜 |
| 0 条 | 告知"未找到相关记忆" |

## 反思规范

### 触发条件

- 累计 5-8 条新记忆后
- 完成一个功能模块后
- 出现重大 bug / 走了弯路后
- 项目里程碑节点
- 用户明确要求

### 反思四步法

1. **回顾**：这段时间做了什么？遇到什么？学到什么？
2. **提炼**：哪些经验是通用的？哪些做法是错的？
3. **整理**：有没有重复/冲突/过期的记忆？
4. **展望**：还有什么知识缺口？下一步优先级？

### 质量检查

- [ ] 至少 3 条可复用的通用经验？
- [ ] 至少 2 个踩坑/反模式？
- [ ] 记忆库做了实际整理？
- [ ] 有具体的后续计划？
- [ ] 反思结论是可执行的，不是空话？

## 价值过滤（VFM）

在 evolve/cleanup/反思时，判断每条候选是否值得投入。

### 打分表

| 维度 | 权重 | 问题 |
|------|------|------|
| 高频复用 | ×3 | 这个知识/模式以后会反复用到吗？ |
| 减少失败 | ×3 | 记下来能避免重复踩坑吗？ |
| 可搜索性 | ×2 | 内容含足够关键词/实体名，未来搜索能命中吗？ |
| 用户负担 | ×2 | 能让用户以后少说/少解释吗？ |
| 自省钱 | ×2 | 能为未来省 token 或少搜索一次吗？ |

**总分 = 各维度得分(0-10) × 权重。总分 < 50 → 不做。**

### 使用场景

| 操作 | VFM 用法 |
|------|---------|
| `mw evolve` | 对每个候选打分，< 50 的标注 skip 理由，不执行 |
| `mw cleanup` | Cold 且关联少的记忆直接清理；cold 但关联多的打 VFM 分决定 |
| 反思时 | 对"下一步优先级"列表现打分，得分高者先做 |

## 边界情况

| 情况 | 处理 |
|------|------|
| 新旧记忆冲突 | 保留两者，旧的标 deprecated，注明替代关系 |
| 内容高度重复 | 合并为一条，保留最完整的版本 |
| 记忆过期失效 | 不删除，标 deprecated + 过期原因 |
| 不确定要不要记 | 先记，标 draft，反思时再处理 |

## 跨会话上下文恢复协议

> Agent 关闭后新开窗口如何接续上次的工作。详细参考文档见 [会话生命周期](references/session-lifecycle.md)。

### 核心原则

- session 记忆是**按需读取**的，不是自动加载的（不占 Always-Load 额度）
- 新会话启动时**只读最新 1 条**，不会一次性加载全部
- 旧 session 记忆通过 `mw decay` 自然老化，不需要手动清理
- 重要的 session 内容**主动 `mw update --scope project`** 转长期，不依赖 session 过期

### 写入规则

| 写入时机 | 内容 | 频率控制 |
|----------|------|---------|
| 一个子任务完成 | 本轮改动 + 状态 + 下一步 | 必写 |
| 即将 context compact | 同上 | 必写（hooks 自动触发） |
| 用户说"先到这" | 最终状态 + 待办清单 | 必写 |
| 每轮对话 | ❌ 不写 | 太频繁，噪音 |
| 纯探索没有结论 | ❌ 不写 | 没价值 |
| 修了个小 typo | ❌ 不写 | 不值得记 |

> **频率控制原则**：一条 session 快照应该覆盖 "一小段完整工作"——不是每句话，也不是整个项目。一个子任务 = 一条。

### 过期与老化

session 记忆天然比 project/global 更容易过期：

| 机制 | 效果 | 自动/手动 |
|------|------|-----------|
| `mw decay` 权重衰减 | 超过 X 天未被访问 → weight 降低 → 搜索结果排名靠后 | 自动 |
| `mw evolve` 冷热升降级 | session 记忆长期不访问 → 自动降为 cold → 不参与常规搜索 | 自动 |
| `mw cleanup` 清理 | 清理 cold 且无关联的 session 记忆 | 手动 |
| `mw update <doc_id> --scope project` | 将 session 记忆晋升为 project scope | 手动 |

**老化逻辑**：`mw decay` 对所有 scope 统一按未访问天数衰减权重。session 记忆因为跨会话后不被读取，权重自然快速沉底。你不需要记住具体数字，只要知道：**session 记忆会自然沉底，重要内容手动 `mw update --scope project` 就行。**

### 读取规则

| 场景 | 命令 | 加载量 |
|------|------|--------|
| 新会话启动 | `mw list -c "会话快照" -n 1` → 读最新一条完整 content | ~200 tokens |
| 顺着项目名搜 | `mw search "会话快照 <项目名>"` → 取最新 | ~50 tokens |
| 翻之前的历史快照 | `mw list -c "会话快照"` → 按需读旧记录 | 多，但可控 |

**关键：session 记忆不会自动注入会话上下文**，只有 Agent 明确搜索/读取时才会消耗 token。下个会话启动时 Agent 读**最新 3 条**的 compact_content 形成摘要链，需要细节时才读完整 content。

### 晋升路径

session 快照中的内容如果有长期价值：

```bash
mw update <doc_id> --scope project    # session → project（常用）
mw promote --min-weight 50 --min-access 5   # 批量：project → global
```

单条晋升用 `mw update`，批量晋升用 `mw promote`（自动筛选 weight+access 达标的 project 记忆升为 global）。

当同一知识点在 session 快照中出现 2 次以上，就应该晋升：持续的才是规律，一次性的才是 session。

### 恢复流程

新会话启动或 context 压缩后，按以下顺序恢复上下文：

1. `mw list -c "会话快照" -n 3` — 读**最新 3 条** session 的 compact_content，形成"之前做 A → 遇到 B → 现在是 C"的摘要链
2. 如果最新 3 条跨不同项目/任务 → 按时间分段理解，分别汇报每段上下文
3. `mw search "project <项目名>" -n 3` — 读项目当前进展
4. 第 3 步结果 < 3 条 → `--graph` 展开图谱
5. 向用户汇报："上次在修 X，进展到 Y，下一步是 Z"
6. 全都没找到 → "找不到之前的上下文，从头开始"
